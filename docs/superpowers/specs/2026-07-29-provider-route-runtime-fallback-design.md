# Provider 专用路由运行时回退设计

## 背景

供应商“测试连接”使用 `chat` 专家路由，而知识库初始化使用 `project_lead` 专家路由。用户可以为每个专家钉选独立的供应商和模型，因此连接测试成功只能证明目标供应商的 `chat` 路线可用，不能证明 `project_lead` 的专用模型可用。

设置页已承诺“专用服务商不可用时会自动回退”，但当前 `ProviderRouter.routesFor()` 命中专家覆盖后只返回专用路线。该路线发生模型不可用、限流、临时服务故障、运行时故障或协议错误时，`execute()` 没有默认路线可继续尝试，最终仅返回“所有已配置 AI 服务暂时不可用”。`ProviderExecutionError.detail` 中保存的最后失败原因也没有进入 `PiRunner` 的错误事件，导致知识初始化无法展示可行动的诊断。

## 目标

1. 专用供应商或模型在运行时失败后，继续尝试默认有序路由。
2. 默认路由允许使用同一供应商的默认模型，也允许降级到其他供应商。
3. 专用模型与默认模型具有独立的健康状态，避免相互覆盖熔断结果。
4. 所有候选路线均失败时，知识初始化展示泛化错误和最后一次已脱敏、已限长的底层原因。
5. 保持 `task_result` 与 `interaction` 错误立即终止，不因结果校验或用户交互而切换供应商。

## 非目标

- 不把“测试连接”扩展为逐一运行所有专家画像。
- 不删除或自动改写用户的 `project_lead` 专用配置。
- 不改变 Provider 级 `workloadModels[expert] ?? defaultModel` 的解析优先级。
- 不改变鉴权失败按供应商隔离、总尝试次数上限和现有冷却时长。

## 路由设计

### 候选顺序

当存在有效的 `AgentModelOverride` 时，路由候选按以下顺序生成：

1. 专用供应商和专用模型。
2. 当前已启用供应商按优先级生成的默认专家路线。
3. 删除与专用路线完全相同的 `providerId + model` 候选，避免重复调用。

“专用配置有效”仅表示配置、凭证和当前健康状态允许尝试，不代表远端模型一定可执行。专用路线成功时不会触发任何后备路线；只有现有可降级错误分类才会继续。

`onlyProviderId` 在完整候选生成后过滤，因此测试某个未被 `chat` 专用配置选中的供应商时，仍能使用该供应商的默认模型完成连接测试，且绝不切换到其他供应商。

### 健康状态隔离

默认路线继续使用现有 `providerId:expert` 标识，兼容已有健康记录。专用路线使用包含模型稳定摘要的独立标识：

```text
providerId:expert:override:modelDigest
```

这样专用模型的 `model_unavailable` 熔断不会阻止同一供应商的默认模型，也不会被默认模型成功错误清除。用户更换专用模型后摘要变化，新模型可立即尝试；删除专用配置后默认路线不受旧专用健康记录影响。

### 错误分类

- `model_unavailable`、`rate_limit`、`transient_provider`、`runtime`、`protocol`：记录当前路线失败并尝试下一候选。
- `authentication`：记录供应商级鉴权失败，跳过该供应商的其余候选，再尝试其他供应商。
- `task_result`、`interaction`：立即返回原错误，不进行回退。

路由总调用次数仍受现有 `MAX_ATTEMPTS` 限制。

## 错误展示

`ProviderRouter` 继续用稳定的用户提示作为主错误，并在 `detail` 中携带最后一次失败原因。`PiRunner` 在生成 `AgentEvent.error` 时追加非重复的 `detail`，限制最大长度；该信息来源于已经过 Translator 或 Supervisor 密钥脱敏的 Provider/进程诊断。

知识协调器沿用现有失败记录逻辑，把最终错误写入 `knowledge_runs.diagnosticsJson` 并通过 IPC 返回。用户看到的信息应同时包含：

```text
所有已配置 AI 服务暂时不可用，请稍后重试：<最后一次脱敏根因>
```

不得包含 API Key、凭证引用或未经脱敏的请求头。

## 测试策略

### ProviderRouter

- 专用 `project_lead` 模型失败后，回退到同一供应商默认模型。
- 同一供应商默认模型继续失败后，回退到下一供应商。
- 专用模型成功时不调用默认路线。
- 专用路线与完全相同的默认候选去重。
- 专用路线与默认路线使用不同健康标识，默认成功不清除专用模型熔断。
- 鉴权失败跳过同一供应商的默认模型。
- `task_result` 和 `interaction` 不回退。
- `onlyProviderId` 可以测试未被 `chat` 专用配置选中的供应商，并且不跨供应商。

### PiRunner 与知识初始化

- 路由耗尽时错误事件包含稳定主提示和最后一次脱敏根因。
- 根因长度受限且不重复主提示。
- `startInitialization()` 失败后将同一诊断写入失败运行记录。
- 现有知识初始化成功、确认、取消与清理测试继续通过。

## 验收标准

1. `chat` 连接测试成功、`project_lead` 专用模型不可用时，初始化会自动使用默认路线继续执行。
2. 有可用默认路线时，不再向用户返回“所有已配置 AI 服务暂时不可用”。
3. 所有路线确实失败时，错误信息包含可定位的脱敏根因。
4. 供应商健康状态、调用统计和尝试顺序与实际执行路线一致。
5. Core、Agents、Scheduler 和 Desktop 相关回归测试及全仓类型检查通过。
